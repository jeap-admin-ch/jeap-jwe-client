# Local branch review — feature/JEAP-7096-context-path-readiness vs main

_2026-07-03 · base merge-base `e670074f16` · head `a55ccc64e2` · incl. uncommitted changes · 13 file(s) changed · 3 findings (0 high / 2 medium / 1 low)_

**Goal.** Make the backend-published include/exclude patterns the authoritative gate for JWE protection by deferring include decisions until the backend configuration is loaded (fixing plaintext leaks for backends under a servlet context path) and failing closed with JWE_CONFIG_LOAD_FAILED when that configuration cannot be loaded; release as 1.2.0.

**Assessment.** The implementation is clean and matches the stated intent: only genuinely origin/exclude-based short-circuits happen pre-config, loadBackendConfig:false and SSR paths behave as before, recursion is prevented by the HttpBackend-based config/JWKS clients, and new interceptor and matcher tests plus docs/changelog are consistent. Two issues remain: the pre-config exclude short-circuit relies on client default excludes that are not guaranteed to be in the effective exclude list (a residual, narrow plaintext-send window that contradicts the 'only stable decisions locally' invariant), and shipping a fail-closed, availability-affecting behavior change as a minor version bump understates the upgrade risk.

## Medium

| Finding | Description | Resolve |
| --- | --- | --- |
| M1 | The pre-configuration exclude short-circuit is not actually stable: it lets client default excludes make a final plaintext decision even though they are dropped from the effective configuration once the backend publishes excludedPaths. The interceptor passes a request through when it matches the local snapshot's excludes (projects/jeap-jwe-client/src/lib/interceptor/jeap-jwe.interceptor.ts:56 via isRequestExcluded, projects/jeap-jwe-client/src/lib/matcher/jwe-endpoint-matcher.ts:92), and that snapshot contains DEFAULT_EXCLUDED_PATHS ('/.well-known/**', '/actuator/**', '/health'). But resolveExcludedPaths (projects/jeap-jwe-client/src/lib/config/jeap-jwe-defaults.ts:93-94) replaces those defaults with the backend's excludedPaths when the backend publishes them, so the client defaults are broader than the effective list — e.g. a backend with includedPaths ['/**'] whose built-in excludes only cover its specific '/.well-known/jwks.json'/'/.well-known/jwe-configuration' endpoints would protect a POST to another '/.well-known/...' or '/health' path, while the client sends it in plaintext. This is exactly the class of silent-plaintext bug the branch sets out to eliminate, and the comment at jeap-jwe.interceptor.ts:36-38 ('the default excludes mirror the backend's built-in excludes') overstates the guarantee. Fix: restrict the pre-config short-circuit to patterns guaranteed to be in the effective exclude list — the local `exclude` option plus the resolved jweConfigPath/jwksPath endpoints — and defer default-exclude matches to the effective configuration (or at minimum document the residual assumption and add a test for a backend whose published excludes are narrower than the client defaults). | yes |
| M2 | A behavior change that can hard-fail previously working requests is shipped as a minor version bump (1.1.0 -> 1.2.0, projects/jeap-jwe-client/package.json:3), so consumers on '^1.1.0' pick it up automatically. With loadBackendConfig enabled (the default), every same-origin, non-excluded request — including ones outside the include patterns that were previously forwarded immediately, e.g. HttpClient fetches of assets/i18n files on a same-origin SPA — now (a) waits for the first backend-config load and (b) fails with JWE_CONFIG_LOAD_FAILED whenever the config endpoint is missing or down, instead of being sent. For apps whose backend does not serve /.well-known/jwe-configuration, all same-origin HttpClient traffic breaks on upgrade until they set loadBackendConfig:false or add excludes. The changelog (projects/jeap-jwe-client/CHANGELOG.md:93-104) documents this honestly, but under SemVer a backwards-incompatible behavioral change warrants a major bump. Fix: release as 2.0.0 (updating publiccode.yml accordingly), or if 1.2.0 is a deliberate policy choice, add an explicit migration/upgrade-risk note to the changelog and README calling out the loadBackendConfig:false / exclude escape hatches. | yes |
